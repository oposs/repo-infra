# Changelog fragments (D40)

Decision: D40 (a repository may collect its changelog entries as fragment
files, which the release pull request rolls into `CHANGES.md`; keeps D2's
required gate, D6's format and D28's release flow). Issue: #172.

## Intent

Every pull request adds its entry under `## [Unreleased]` in `CHANGES.md`.
When several pull requests are open, each merge makes the next one conflict
there, and the strict status check policy then forces a rebase and a full CI
run. In oposs/thinfloe on 2026-11-20, four feature pull requests (#35 to #38)
merged one after the other, and `CHANGES.md` conflicted at almost every
rebase. The conflicts are trivial, but each one needs a person or an agent.

With fragments, a pull request adds its entries in its own files and never
touches `CHANGES.md`. Two pull requests then never edit the same file.

## Decisions by the owner

- Each repository decides whether it uses fragments. There is no single
  shape for all repositories.
- `CHANGES.md` itself says so: a note at its top names the directory where
  pull requests put their fragments. The note is the switch. There is no
  key in `.github/repo-infra.json`.
- With fragments active, a change to `CHANGES.md` outside a release pull
  request is an error, with one exception: a change inside an already
  released section (a typo, a wrong issue tag in `## 2.16.0`) is allowed.
  The owner accepts that this lets someone add a line to the latest released
  section.

## Goals

- A repository with the note gets the fragment rules in the gate, in the
  release pull request and in `check`. A repository without the note works
  exactly as today.
- No change to the v2 interface (D33): no new input, no new permission, no
  change to the caller `changelog.yml`.
- `apply` switches a repository over on a branch, in one pull request.
- repo-infra itself switches to fragments in the pull request that brings
  this change (owner's decision). Its own gate runs the piece at the commit
  under test, so that pull request is judged by the new switch rule, and the
  next repo-infra release is the first one rolled from fragments.
- The release notes of a fragment release look the same as the release notes
  of a classic release.

## Non-goals

- Switching a repository back from fragments to `[Unreleased]`. That is a
  hand edit; the gate only makes sure no fragment is lost on the way (see
  Gate).
- Readers of `[Unreleased]` between releases ("what's new" screens). Each
  such reader is its repository's concern; thinfloe's Upgrade screen reads
  released sections only.

## Anti-goals

- A fragment that the release silently drops. Every way a fragment can leave
  the tree outside a release pull request fails the gate, and the release
  pull request deletes exactly the fragments it rolled.
- A second source of truth. `CHANGES.md` stays the file that `ri-publish-tag`,
  `ri-release-finish` and `release-publish.yml` read. Fragments exist only
  between releases.

## Approaches

- **Collect at the release pull request (chosen).** `ri-release-prepare`
  reads the fragments, writes the new section and deletes the fragments in the
  release commit. Nothing on `main` moves between releases except the
  fragment files.
- **Collect each fragment when its pull request merges.** Dropped: a bot
  would push a commit to `main` after every merge, which goes around branch
  protection and puts every open pull request behind `main` again, the
  problem #172 removes.
- **An outside tool such as towncrier.** Dropped: a second file format and a
  Python dependency in every repository, next to the `changes.js` library
  every piece already loads at its own commit (D33).
- **A key in `.github/repo-infra.json` as the switch.** Dropped by the owner:
  the changelog itself must tell a contributor where entries go.

## The note

The note is a paragraph in the header of `CHANGES.md`, the part above the
first `## ` heading. Its first line starts with `Changelog fragments: `
followed by the directory in a code span. `apply` writes this text:

```markdown
Changelog fragments: `CHANGES.d/`. Pull requests do not edit this file. Each
pull request adds its entry as a file in `CHANGES.d/new/`,
`CHANGES.d/changed/` or `CHANGES.d/fixed/`. The release pull request moves
the entries into this file.
```

The tools match this pattern on a header line and take the directory from
it:

```
^Changelog fragments: `([^`]+?)/?`
```

The rest of the paragraph is for people. (My call:
a fixed lead-in is both readable and unambiguous; an HTML comment would hide
the switch from the reader the owner wants to reach.)

The directory is a relative path inside the repository. The tools refuse a
directory that is absolute, contains `..`, is `.github` or lies under it,
or is `CHANGES.md`. `apply` uses `CHANGES.d`.

With the note present, `CHANGES.md` has no `## [Unreleased]` heading. A file
with both is refused by the gate and by `roll` ("the switch to fragments is
not finished").

## Fragments

- A fragment is a file `<dir>/<section>/<name>.md`, where `<section>` is
  `new`, `changed` or `fixed`. These map to `### New`, `### Changed` and
  `### Fixed` (D6).
- A fragment holds one or more entries, written to the rules of the
  `writing-style` skill. Each entry is a Markdown list item: a line that
  starts with `- `, followed by continuation lines indented by two spaces.
  A branch can collect all its entries of one section in one file; a branch
  with new features and fixes has one file in `new/` and one in `fixed/`.
- Refused (by the gate, and by `roll` as the backstop): a fragment without
  an entry, a line that starts with `#` (a heading), and text that is not
  part of a `- ` entry. Blank lines between entries are allowed and dropped.

### Names

A fragment's name is a UTC timestamp to the minute, 4 random hex
characters and a topic:

```
CHANGES.d/new/20261126-0921-a3f9-time-band.md
```

The gate checks the pattern `^[0-9]{8}-[0-9]{4}-[0-9a-f]{4}-[a-z0-9]+(-[a-z0-9]+)*\.md$`.
A shell makes the prefix with `date -u +%Y%m%d-%H%M` and
`openssl rand -hex 2`.

The owner asked for a name that clashes with high probability never, that
needs no pull request number (entries are collected on a branch before it
is pushed) and that stays simple. Two contributions rarely share a minute;
the random part makes a clash 1 in 65,536 even then. The random part stands
in for a place: a host or user name would stay in the Git history after the
release deletes the file, and repo-infra is public.

- Refused: any other file under `<dir>/new`, `<dir>/changed` or
  `<dir>/fixed` (a name that breaks the pattern, a subdirectory), and any
  other directory under `<dir>`. Files directly in `<dir>` are allowed;
  `apply` puts a `README.md` there, which keeps the directory alive when a
  release empties the section directories, and which repeats the naming rule.
- The order within a section is by file name, compared as plain strings
  (JavaScript's default sort), so the oldest fragment comes first. Inside a
  fragment the entries keep their order.

## Roll

`roll` takes the text of `CHANGES.md`, the version, the date and, in fragment
mode, the list of fragments as `{ section, name, text }`. It reads the mode
from the note.

- Classic mode: unchanged.
- Fragment mode: the new section is `## X.Y.Z - date`, then `### New`,
  `### Changed`, `### Fixed` in that order, each only when it has entries.
  Each section lists the entries of its fragments in fragment order, as they
  are written, with the blank lines between entries dropped. Blank lines
  around headings follow the layout #163 introduced (a blank line after each
  heading and after each subsection). The section goes directly after the
  header, before the first released section. The header is kept byte for
  byte.
- No fragments: `roll` throws "no changelog fragments in `<dir>` - nothing
  to release", the backstop behind the gate, as today for an empty
  `[Unreleased]`.

## Release pull request

- `ri-release-prepare` reads the note from the checked-out `CHANGES.md`,
  lists the fragments from the checkout, rolls, and commits `CHANGES.md`, the
  version files, and a deletion of every fragment it rolled.
- `commit.js` `commitFiles` takes a new optional list `deletions`. Each path
  becomes a tree entry with `sha: null`, which the Git Data API reads as a
  deletion.
- `ri-release-finish`: the pull request body says "collects N entries from
  `<dir>/` into `## X.Y.Z - date`" instead of "rolls `[Unreleased]`", and
  the `changelog-updated` check title and summary say the same.
- `release.js` `refusedReleaseFiles` and `check.py`
  `refused_release_files` also refuse any path under the fragment directory,
  so the build artifact cannot write fragments into the release.
- The abandon messages (`untaggedMessage`, `treeVerdict` in `release.js`, and
  the "no release-build.json" message in `publish.js`) say in fragment
  mode: "merge a pull request that removes the `## X.Y.Z` section from
  CHANGES.md and restores its fragments". The gate allows that pull request
  (see below).
- `release-publish.yml` filters on `paths: [CHANGES.md]`. An ordinary merge
  in fragment mode changes no `CHANGES.md`, so no publish run starts; a fix
  to an old entry starts one, which finds the latest release tagged and does
  nothing, as today.

## Gate

`ri-changelog` reads `CHANGES.md` at head and at the merge base of the pull
request (`compareCommitsWithBasehead`, `merge_base_commit`), not at the tip
of `main`. (My call: `pulls.listFiles` diffs against the merge base, and
against the tip every open fragment pull request would fail after each
release, because `main` has a `## X.Y.Z` heading the branch lacks. The mode
is read from the merge base for the same reason: a pull request opened before
the switch is judged by the classic rules.) The classic rules keep reading
`pr.base.sha` as today. In fragment mode it also lists the pull request's changed files
(`pulls.listFiles`, paginated; the piece already has `pull-requests: read`)
and reads each added or changed fragment at head. `changes.js` gets the
verdict as a pure function of these inputs.

The mode comes from the note at head and at the merge base:

- **Both without the note:** classic rules, unchanged.
- **Both with the note (fragment mode):**
  - The header must be identical at base and head, and the list of `## `
    heading lines must be identical too. Lines inside released sections may
    change. A pull request that adds a section, or edits the note, fails.
  - Exception: the pull request may remove the topmost released section when
    its version has no `v<version>` tag (the abandon route above). The gate
    reads the tags for this one case only. It must then add at least as many
    entries in fragments as the removed section had (top-level `- ` lines).
    (My call: a count, not a text match, catches a forgotten restore without
    a matching engine.)
  - Every added, changed or renamed file under `<dir>` must pass the
    fragment rules above.
  - A deleted fragment fails ("removes CHANGES.d/fixed/x.md, which another
    pull request added"). A rename inside the section directories is allowed:
    it moves an entry, it does not lose one. A deletion of a fragment that the
    same pull request added never shows in the file list, so a pull request can
    rework its own fragments freely.
  - The pull request passes when it adds, changes or renames at least one
    fragment, or when it changes released text only (a fix to an old entry).
    It fails when it does neither: "This pull request adds no changelog
    fragment. Add one under `CHANGES.d/<section>/`, or label the pull request
    'no-changelog'".
- **Note at head, not at the merge base (the switch):** passes when the head
  has no `[Unreleased]` heading, the released sections are unchanged, every
  fragment passes the fragment rules, and the pull request adds at least as
  many entries in fragments as `[Unreleased]` had at the merge base (same count
  rule as the abandon route, my call). It needs no further entry.
- **Note at the merge base, not at head (switching back):** classic rules for the head,
  and it fails while fragment files remain under the old directory.

The `no-changelog` label keeps skipping the whole gate, as today. The
caller `changelog.yml` skips the job at job level, so with the label none of
the fragment rules run either. (My call: the label is the deliberate human
override, and changing it would mean a new `changelog.yml` in every
repository.)

## check and apply

- `check` reports the mode as an item. In fragment mode it reports drift: the
  directory named in the note is missing, `[Unreleased]` is still present,
  or a file under the section directories breaks the fragment rules.
- `apply --item changelog-fragments` switches a repository on its branch:
  it writes the note into the header, removes the `[Unreleased]` block,
  writes the entries of each subsection into one fragment of that section
  (`<dir>/<section>/<timestamp>-<random>-unreleased.md`), in their old order, and writes `<dir>/README.md`. It is
  never applied without being named, since the choice is the repository's.
- `apply` does not rewrite an entry that the fragment rules cannot hold (a
  heading inside it, text outside a list item, a subsection other than New, Changed or
  Fixed such as `### Removed`). It refuses the switch and names each such
  entry. `commands/apply.md` tells the agent to rewrite those entries in
  `CHANGES.md`, show the rewrite to the owner, and run the item again. (My
  call: the script stays lossless, and the judgment over prose stays with the
  agent.)
- `commands/apply.md` tells the agent to update the repository's own
  instructions (`CLAUDE.md`, `CONTRIBUTING.md`) that say "update
  CHANGES.md": the entry goes into a fragment. The agent judges the text; no
  script parses it.

## Documentation

- The `writing-style` skill, section "Changelog entries": in a repository
  whose `CHANGES.md` carries the note, entries go into fragment files; one
  or more `- ` entries per file, no heading, the name made by the naming rule
  above.
- `references/conventions.md` (D40 section), `references/release-flow.md`,
  the headers of `ri-changelog` and `ri-release-prepare` ("Supplies:"), and
  `make catalogue` after the header change.

## Testing

- `changes.test.js`: note parsing and directory refusals; fragment rules;
  roll in fragment mode (order, continuation lines, empty sections left out,
  header kept); every gate case above, including the abandon exception and
  both switch directions.
- `commit.test.js`: deletions become `sha: null` entries.
- `release.test.js` and the Python tests: refused release files under the
  fragment directory, kept in step between JS and Python.
- Python tests for the `check` items and for `apply --item
  changelog-fragments` on a fixture repository.
- One end-to-end run on oetiker/repo-infra-spike before the release: switch it
  with `apply`, open two pull requests with fragments, merge both without a
  rebase conflict, dispatch Create release PR, and read the rolled
  `CHANGES.md` and the draft release notes.
