# Project shape: what a repository contains, and the pieces that build it

Date: 2026-10-10
Status: draft for review
Decision: D32 (adds a project shape on top of D30; changes nothing in the release flow of D28 and D31)

## Why

The standard says how a repository is built, tested and released. It says
nothing about what a released project should contain. D22 and D23 leave musl
builds and man pages to the caller's choice, and onboarding suggests a man page
only when `docs/manual.md` already exists.

The result is visible across the terminal tools onboarded so far:

- mdmost, edaptor and mtuspy each carry their own copy of the same release
  build (binaries, `.deb`/`.rpm`, Homebrew bottles, formula rewrite). The three
  copies have drifted: only edaptor and mtuspy build illumos, only mtuspy builds
  Windows arm64, and mtuspy's illumos leg asks for `crt-static`, which illumos
  does not have.
- Their READMEs install the apt key under two different names
  (`gitea-oposs.asc`, `oposs.asc`), only some create `/etc/apt/keyrings` first,
  and edaptor omits `brew trust`, which Homebrew 6 needs (#57).
- Only mtuspy shows a CI and a release badge. ansidrama shows CI only; edaptor
  and mdmost show none.

## Decisions

- **A project has a shape.** A base applies to every repository; every other
  rule is attached to a trigger that describes the project, such as "has a
  command line" or "compiles to a native binary". A repository matches as many
  triggers as apply to it. SmokePing, for example, has a command line, a web
  interface and runs on an interpreter with native modules.
- **The LLM judges the shape; the script measures pieces.** The shape is prose
  in the skill. The LLM decides which triggers apply, reads the README, the
  manual, the demo and the release build, and reports. No script detects the
  kind of project, judges a README or parses the exceptions.
- **Every rule applies unless an exception says why not.** Exceptions live in
  `.github/repo-infra.json`, one reason per rule id.
- **The shape review is part of `check`.** `/repo-infra:check` runs the script
  and then the shape review, and reports both. Onboarding uses the same review
  to plan the work.
- **The archive is the contract between the release pieces.** Only the binaries
  piece knows the language. Packaging and Homebrew read the archives it built.
  repo-infra has CI pieces for Go, Node, Perl and Python as well as Rust; a
  later Go binaries piece meets the same contract and reuses the rest.

## The shape

The shape lives in a new reference, `skills/repo-infra/references/project-shape.md`.
Each rule there has an id (also its exception key), a trigger, what it
requires, how the LLM verifies it, and what meets it.

### Base: every project

- `readme-current`: The README describes the project as it is now. The LLM
  compares it with the manual or `--help`, with the channels in
  `release_assets` and `gitea_packages`, and with the supported platforms, and
  reports features that are missing, options that no longer exist and channels
  that are not mentioned.
- `badges`: The top of the README shows the CI badge
  (`https://github.com/<owner>/<repo>/actions/workflows/ci.yml/badge.svg`,
  linked to the workflow) and the version badge
  (`https://img.shields.io/github/v/release/<owner>/<repo>`, linked to the
  latest release). `project-shape.md` carries the snippet. Other badges may
  follow.
- `install-text`: A project that publishes has one install section with the
  canonical snippet for each channel it publishes to (below).
- `writing-style`: The README, `docs/manual.md`, the rest of `docs/` and the
  unreleased section of `CHANGES.md` follow the `writing-style` skill. The LLM
  loads that skill and reports each violation with its file, the quoted text
  and the rule. For a large documentation site it reads the README and the
  manual in full, samples the rest, and says that it sampled.

### Has a command line

- `man-page`: `docs/manual.md`, built by the `man` pieces and checked by
  `ri-ci-man`. Onboarding asks for it; it does not wait for the file to exist.

### Runs in a terminal (CLI or TUI)

- `demo`: An ansidrama script `demo/<name>.toml`, the rendered
  `docs/demo/<name>.webp` near the top of the README, and a `make demo` target
  that renders it. The WebP is committed and regenerated by hand. The LLM
  reports a demo that shows commands or screens that no longer exist.

### Has a web or graphical interface

- `screenshot`: A current image of the interface near the top of the README.

### Compiles to a native binary

- `native-targets`: Archives for `x86_64-unknown-linux-musl`,
  `aarch64-unknown-linux-musl`, `x86_64-apple-darwin`, `aarch64-apple-darwin`,
  `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc` and
  `x86_64-unknown-illumos`, named `<name>-<version>-<target>.tar.gz` (`.zip`
  for Windows). mise's `github:` backend picks an asset by these names, so
  `mise use -g github:<owner>/<name>` works without further setup (tested on
  edaptor 1.8.0).
- `linux-packages`: `.deb` and `.rpm` for amd64 and arm64, built from the
  musl archives, published to the Gitea registry by `ri-publish-gitea`.
- `homebrew`: `Formula/<name>.rb` in the repository, which is its own tap,
  with bottles for macOS.

### Runs on an interpreter

- `source-archive`: The source archive of the release (`make dist` for
  autotools, through `ri-release-source-tarball`).
- `linux-packages`: `.deb` and `.rpm`. Per architecture when the package
  bundles native modules (SmokePing's `thirdparty/` compiles XS modules such as
  `FCGI` and `Socket6`), `noarch` when it depends on distribution packages
  instead.
- `homebrew`: A formula that builds from the source archive.

No piece in this design builds the interpreted variants beyond what
`ri-release-source-tarball` and `ri-release-nfpm` already cover. The SmokePing
onboarding proves the rest first (`teaching-the-standard.md`).

## Exceptions

`.github/repo-infra.json` gains one key:

```json
"exceptions": {
  "homebrew": "a service that needs root and a web server; brew is the wrong channel"
}
```

The value maps a rule id to a reason. The script accepts the key and reports a
`problem` when the value is not an object whose values are non-empty strings.
It does not know the rule ids. An exception whose id matches no rule, or a gap
that has no exception, is reported by the shape review.

A piece input that drops a requirement, such as `skip_targets` below, is
allowed only together with an exception for the rule it weakens. The shape
review checks that pairing.

## The shape review

`commands/check.md` gains a second step after the script report:

1. Read `references/project-shape.md`.
2. State which triggers apply, each with its evidence ("has a command line:
   `src/main.rs` parses arguments with clap").
3. Give every rule of those triggers one state: `met`, `gap` with what is
   missing, or `excepted` with the recorded reason.
4. List exceptions that match no rule.

The script's exit code stays what it is. The shape review is a separate part of
the report and does not change it.

`references/onboarding.md` gains a step: run the shape review, then agree with
the owner which gaps this run closes and which become exceptions.

## Install snippets

`project-shape.md` holds one canonical snippet per channel, with `<owner>` and
`<name>` to fill in. These settle the differences #57 lists.

- Debian and Ubuntu: create the keyring directory first, and use the key name
  `gitea-oposs.asc` (the name in `release-flow.md`, edaptor and mtuspy):

  ```sh
  sudo install -d -m 0755 /etc/apt/keyrings
  sudo curl -fsSL -o /etc/apt/keyrings/gitea-oposs.asc https://gitea.oetiker.ch/api/packages/oposs/debian/repository.key
  echo "deb [signed-by=/etc/apt/keyrings/gitea-oposs.asc] https://gitea.oetiker.ch/api/packages/oposs/debian stable main" | sudo tee /etc/apt/sources.list.d/oposs.list
  sudo apt update && sudo apt install <name>
  ```

- Fedora, RHEL, Rocky, Alma: one command for dnf4 and dnf5 alike:

  ```sh
  sudo curl -fsSL -o /etc/yum.repos.d/oposs.repo https://gitea.oetiker.ch/api/packages/oposs/rpm.repo
  sudo dnf install <name>
  ```

- Homebrew:

  ```sh
  brew tap <owner>/<name> https://github.com/<owner>/<name>
  brew trust --formula <owner>/<name>/<name>
  brew install <name>
  ```

  with one sentence that `brew trust` exists from Homebrew 6 on.

- mise: `mise use -g github:<owner>/<name>`.
- Direct download: a link to the latest GitHub release.

`release-flow.md` replaces its "What users type" block with a pointer to these.

## Pieces

Three new pieces, each at v1. mdmost, edaptor and mtuspy are the proof for the
binaries and Homebrew pieces (teaching stage 2): all three run the same jobs
green. Smalti is the proof for nfpm. The archive layout is the contract:

```
<name>-<version>-<target>.tar.gz
  <name>/<name>
  <name>/man/<name>.1
  <name>/README.md
  <name>/LICENSE
  <name>/<extra paths>
```

The Windows `.zip` has the same layout without `man/`.

### `ri-release-rust-binaries`

Lifted from the three copies.

- Inputs: `version`, `ref`, `bin`, `extra_paths` (space-separated repository
  paths copied into the archive, for example `examples` or `integrations`),
  `skip_targets` (space-separated; requires an exception for
  `native-targets`), `man` (default true; false requires an exception for
  `man-page`).
- One matrix leg per target of `native-targets`, `fail-fast: false`.
- Linux musl and illumos build with `cross`, pinned by version. Only the musl
  legs set `-C target-feature=+crt-static`.
- `make man` runs on every leg that is not Windows, when `man` is true.
- `cargo build --release --bin <bin> --target <target>`.
- Packs the archive by the contract above and uploads it as
  `release-asset-<target>`.

### `ri-release-nfpm`

The D30 design for this piece stays: `config`, `prepare`, `packagers`, nfpm
pinned by version and SHA256, `SOURCE_DATE_EPOCH` from the committer time of
`ref` and `MTIME` for nfpm's `mtime:` field (nfpm 2.47.0 ignores
`SOURCE_DATE_EPOCH`), `${VAR}` expanded across the whole config by the piece
(nfpm expands only top-level scalars), an unset variable failing the job, every
package read back with `dpkg-deb` or `rpm`, and file names checked against the
shapes `ri-publish-gitea` accepts. Output: `release-asset-packages`.

This design adds one input:

- `archives`: space-separated targets. For each, the piece downloads
  `release-asset-<target>`, unpacks it, and runs nfpm once per target and
  packager with `STAGE` (the unpacked `<name>/` folder) and `ARCH` (`amd64`
  or `arm64`; nfpm translates it for rpm) in the environment. Without
  `archives`, the piece runs `prepare` and nfpm once per packager, as D30
  describes.

A binary tool's caller sets `archives: x86_64-unknown-linux-musl
aarch64-unknown-linux-musl` and lists the binaries job under `needs:`.
Maintainer scripts, such as mtuspy's `setcap` postinst, are referenced from
the repository's `nfpm.yaml`. The file names stay
`<name>_<version>-1_<arch>.deb` and `<name>-<version>-1.<arch>.rpm`, so
`release_assets` does not change.

### `ri-release-homebrew`

Lifted from the three copies.

- Inputs: `version`, `ref`, `name` (the formula, default the repository name).
  The formula is `Formula/<name>.rb`.
- Needs the archives of `aarch64-apple-darwin`, `x86_64-apple-darwin`,
  `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`.
- Bottles on `macos-14` (required) and `macos-15-intel` (optional,
  `continue-on-error`), from a local tap pointing at the built macOS archives,
  with `Homebrew/actions/setup-homebrew@main` and `brew trust` guarded for
  Homebrew 5.
- Renames each bottle from the name `brew bottle` writes to the name its json
  records.
- Rewrites the formula: the `version` line, the four `sha256` lines found by
  their marker comments (`# mac-arm`, `# mac-x86`, `# linux-x86`,
  `# linux-arm`), and the bottle block generated between `# BOTTLE-START` and
  `# BOTTLE-END`. It fails when no bottle was built, when a bottle is missing
  under its recorded name, or when the markers are gone.
- Outputs: the bottles as `release-asset-bottle-<os>`, and the formula as the
  artifact `release-files`. A repository that uses this piece has no other job
  that writes `release-files`.

`project-shape.md` carries a formula template with all markers in place. The
formula belongs to the repository, because it decides what is installed (mdmost
installs `integrations/`, edaptor `examples/`).

## Converting the consumers

One repository per run, by hand, each with the owner's OK:

1. mtuspy: it has not released under the standard yet and is the only one with
   maintainer scripts. Replace the build jobs with the three piece calls,
   translate `[package.metadata.deb]` and `[package.metadata.generate-rpm]`
   into `nfpm.yaml`, run the shape review and close its gaps. Its next release
   is the first real run of all three pieces.
2. edaptor, the same way.
3. Smalti: replace its `packages` job with `ri-release-nfpm`.
4. mdmost, the same way as mtuspy, without a release until the owner says so.

## Testing

Pieces are tested by running them (D19).

- `ri-release-homebrew`: pytest runs the formula rewrite and the bottle-block
  generation as the piece ships them, on a fixture formula, fake archives and a
  recorded `brew bottle --json` output. Cases: two bottles, the optional one
  missing, zero bottles, markers missing, a second run that changes nothing.
- `ri-release-nfpm`: pytest runs the nfpm step in a podman container with the
  pinned nfpm, once on a fixture archive and once in `prepare` mode. The
  archive case compares file list, control fields and the postinst with the
  packages mtuspy v0.1.3's `cargo-deb` build made. The `prepare` case builds
  `noarch` packages from a fixture config shaped like Smalti's.
- `ri-release-rust-binaries`: structure tests (the seven targets, `crt-static`
  only on musl, `skip_targets`, `man`), and the packing step run on a fake
  `target/` tree, checking the archive layout and names.
- `project-shape.md`: a test that every rule has an id, a trigger, a
  requirement and a verification line. `test_no_em_dash.py` and
  `test_prose_skills.py` cover its prose.
- The `exceptions` key: `check` accepts an object of strings and reports
  anything else.

## Order of work

1. The shape without new pieces: `project-shape.md`, the `exceptions` key,
   the shape review in `check.md` and `onboarding.md`, the install snippets and
   the pointer in `release-flow.md`, D32 in `SKILL.md`.
2. `ri-release-nfpm`.
3. `ri-release-rust-binaries`.
4. `ri-release-homebrew`.
5. Catalogue, generations, `CHANGES.md`, a release of repo-infra.
6. The conversions, in the order above.

## Out of scope

- Packaging pieces for interpreted projects beyond `ri-release-source-tarball`
  and `ri-release-nfpm`; the SmokePing onboarding proves them first.
- A Go binaries piece; the contract leaves room for it.
- An entry in the mise registry for short names; it needs a pull request to
  another project per tool.
- Rendering the demo in CI.
- Linux bottles; the formula installs the musl archive on Linux.
